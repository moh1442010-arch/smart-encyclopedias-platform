## 1. هدف المرحلة

إنشاء دورة محاسبية متكاملة وقابلة للتدقيق تربط المستند التشغيلي بمصدره، ثم بالقيد المحاسبي ودفتر الأستاذ العام والأستاذ المساعد وميزان المراجعة والقوائم المالية. يجب أن تكون العمليات ذرية، متوازنة، قابلة لإعادة المحاولة دون تكرار، ومحمية من الترحيل إلى فترة مغلقة.

لا يُعد وجود شاشة أو جدول أو helper برمجي دليلاً على اكتمال الوظيفة. الإغلاق يتطلب تنفيذ المسار الفعلي من واجهة التطبيق وقاعدة البيانات إلى دفتر الأستاذ، واختباراً آلياً ناجحاً على commit محدد.

## 2. حدود العمل

يشمل هذا الملف العيوب D01–D25 فقط:
- D01–D13: الترحيل، الربط، التوازن، منع التكرار، العكس، والفترات المالية.
- D14–D19: ميزان المراجعة ومطابقات العملاء والموردين والنقدية والمخزون والضرائب.
- D20–D22: المرتجعات والإشعارات الدائنة والتسويات الجزئية.
- D23–D25: قائمة الأرباح والخسائر والمركز المالي والتدفقات النقدية.

لا تدخل ضمن هذه المرحلة إضافة خصائص جديدة غير لازمة لقبول هذه الوظائف. تبقى D26–D90 في مراحلها المحددة ولا تُغلق ضمن هذا الملف.

## 3. ترتيب التنفيذ الإلزامي

### الدفعة 1 — أساس الترحيل والضبط (D01–D03)
1. توحيد بوابة الترحيل لكل مصدر محاسبي.
2. إثبات ذرية حفظ المصدر وحدث Outbox.
3. تثبيت هوية الحدث ومفتاح idempotency وبصمة الحمولة وإصدارها.
4. تثبيت ربط الحسابات والفرع والعملة وسعر الصرف قبل أول محاولة ترحيل.
5. رفض الحسابات غير المربوطة أو غير النشطة، والفروع والعملات غير الصالحة، والفترات المغلقة.
6. رفض القيد الأقل من سطرين أو غير المتوازن أو ذي القيم السالبة أو المتجاوزة للنطاق.
7. اختبار إعادة المحاولة والتكرار وتعارض الحمولة وانقطاع التنفيذ.

**بوابة الدفعة:** لا انتقال قبل نجاح اختبارات rollback وduplicate delivery وchanged-payload rejection وbalanced journal وretry recovery.

### الدفعة 2 — ترحيل المستندات التشغيلية (D04–D11)
تنفيذ وربط الترحيل الفعلي لكل من:
- المبيعات.
- المقبوضات والتحصيلات.
- المشتريات.
- المصروفات.
- الإنتاج.
- مراجع المستندات الأصلية.
- العكس المحاسبي بالمستند العكسي.

لكل مسار يجب أن يثبت الاختبار:
- نجاح القيد المتوازن مرة واحدة فقط.
- تطابق المبلغ مع المصدر.
- تطابق طريقة السداد والحساب والفرع والعملة.
- حفظ مرجع المصدر وربطه بالقيد.
- عدم إنشاء أثر جزئي عند الفشل.
- عدم تكرار الرصيد عند إعادة المحاولة.
- منع تعديل أو حذف مستند مرحّل دون مسار تصحيح وعكس موثق.

**بوابة الدفعة:** اختبارات تكامل لكل نوع مستند، مع replay وrollback وsource-to-GL reconciliation.

### الدفعة 3 — الفترات المالية والمطابقات والتقارير (D12–D25)
1. إقفال وفتح الفترات بصلاحيات وسجل تدقيق.
2. منع كل ترحيل إلى فترة مغلقة أو غير موجودة.
3. مطابقة ميزان المراجعة مع قيود الأستاذ العام المرحلة فقط.
4. مطابقة أرصدة العملاء والموردين مع حسابات الرقابة.
5. مطابقة الخزينة وبنكك والبنوك.
6. مطابقة المخزون والضرائب مع حسابات الأستاذ العام.
7. معالجة المرتجعات والإشعارات الدائنة.
8. دعم التحصيل والسداد الجزئيين وتوزيعهما على المستندات.
9. بناء قائمة الأرباح والخسائر والمركز المالي والتدفقات النقدية من أرصدة الأستاذ العام، لا من أرقام منفصلة أو ملخصات واجهة.

**بوابة الدفعة:** سيناريو مالي كامل ينتج ميزان مراجعة متوازناً وقوائم مالية مترابطة، مع تفسير فروق المطابقة وعدم إخفائها.

## 5. ضوابط المحاسبة والبيانات

- استخدام أصغر وحدة نقدية صحيحة وتجنب الحسابات العائمة في المبالغ.
- التحقق من overflow قبل حفظ أي مبلغ أو مجموع.
- كل قيد يتضمن تاريخاً وفترة وفرعاً وعملة ومصدرًا واضحاً.
- لا ترحيل بقيمة صرف افتراضية غير موثقة.
- لا حذف للقيد المرحل؛ التصحيح بالعكس والمستند البديل.
- لا تعديل صامت للمستند بعد ترحيله.
- لا تكرار للترحيل عند إعادة المحاولة أو إعادة فتح التطبيق.
- لا تغيير في package name أو signing certificate أو قواعد البيانات أو سياسة ترقية العملاء.
- بيانات الاختبارات اصطناعية ومعزولة؛ يمنع استخدام بيانات عملاء حقيقية في fixtures.
- لا نشر إلى Worker أو D1 الإنتاجي في هذه المرحلة.

## 6. الاختبارات الآلية المطلوبة

تُقسم الاختبارات إلى:
1. Unit tests للحسابات والتحقق والقيود.
2. Database instrumentation tests للمعاملات والترحيل والتراجع.
3. Integration tests لكل مصدر مالي إلى GL.
4. Reconciliation tests للمساعدات وميزان المراجعة والقوائم.
5. Android emulator tests على API 29 وAPI 35.
6. Regression tests للترقية وحفظ البيانات المتوافقة.

أسماء أوامر Gradle تُثبت من ملفات المشروع الفعلية قبل اعتمادها. لا يُسجل أمر اختبار ناجح ما لم ينفذ على commit نفسه الذي سيُربط به الدليل.

## 7. قاعدة الإغلاق

لا يتحول أي بند إلى CLOSED إلا إذا احتوى سجل D01–D25 على:
- commit SHA محدد.
- أمر الاختبار الفعلي.
- نتيجة PASS من تشغيل مكتمل.
- رابط تشغيل GitHub Actions أو تقرير الاختبار.
- دليل يثبت المسار الفعلي، وليس مجرد نجاح compilation.
- تحقق معايير القبول كاملة.

نجاح Unit tests وحده لا يغلق بند تكامل. ونجاح بناء APK لا يغلق وظيفة محاسبية. وفشل المحاكي لا يُسجل نجاحاً؛ يُشخّص سبب البيئة ثم يعاد التشغيل، مع بقاء اختبار Android شرطاً قبل الإغلاق.

## 8. سياسة التنفيذ والتسليم

- العمل على هذا الفرع أو فرع مشتق منه فقط.
- دفعة واحدة نشطة في كل مرة لتجنب إلغاء تشغيل CI بسبب commits متلاحقة.
- كل دفعة تنتهي بتقرير مختصر: ما تغير، commit، الاختبارات، PASS/FAIL، والعائق المحدد.
- لا دمج PR ولا إصدار تجاري ولا تغيير إنتاجي دون موافقة صريحة.
- لا يُرسل APK للتجربة الميدانية إلا بعد نجاح بوابات المرحلة الأولى والثانية والثالثة، وبناء APK موقع صالح للتحديث، ثم اختبارات الإصدار النهائية.
- بعد إتمام المراحل الثلاث تبدأ المرحلة الرابعة المخصصة حصراً للتصحيح والمراجعة والتجربة الآلية النهائية، ثم تسليم رابط APK للتجربة الميدانية عند النجاح.
