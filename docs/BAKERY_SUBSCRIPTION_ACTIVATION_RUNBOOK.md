# دليل تشغيل اشتراكات الميزان للمخابز

**الإصدار المرشح:** 2.6.17  
**معرّف التطبيق:** `com.mohammedmustafa.almizan.bakery`  
**حالة البيع:** لا تفتح البيع قبل نجاح فحص التوقيع الحي واختبار التفعيل على هاتف.

## دورة العميل

1. يفتح العميل صفحة الاشتراك أو شاشة الاشتراك في التطبيق.
2. يختار شهرياً أو سنوياً أو دائماً، ثم يرسل اسمه ووسيلة التواصل ومعرّف الجهاز ومرجع التحويل.
3. يسجل Worker الطلب بحالة `pending`. لا يصدر رمزاً عند إنشاء الطلب.
4. يراجع المسؤول التحويل فعلياً من بنكك، ويقارن المبلغ بالخطة والمرجع وبيانات العميل.
5. يعتمد المسؤول الطلب من لوحة الإدارة. عند الاعتماد فقط يوقع Worker رمز التفعيل ويربطه بمعرّف الجهاز.
6. يرسل المسؤول الرمز للعميل عبر قناة موثقة. يحتفظ العميل بالرمز؛ لا يُنشر في مجموعة عامة.

## الأسعار المعتمدة

| الخطة | السعر |
|---|---:|
| شهري | 55,000 ج.س |
| سنوي | 550,000 ج.س |
| دائم | 1,050,000 ج.س |

- الشهري ينتهي بعد 30 يوماً.
- السنوي ينتهي بعد 365 يوماً.
- الدائم الجديد مرتبط بإصدار التطبيق وقت الشراء ولا يشمل تحديثات الإصدارات المستقبلية.
- التراخيص الدائمة القديمة المقيدة بـ2.6.15 تبقى مقبولة للتوافق.
- لا تمنح الخطة الشهرية أو السنوية صلاحية دائمة.

## مفاتيح التوقيع

مفتاح ترخيص التطبيق ليس مفتاح توقيع APK. لا تستخدم ملف `smartcompany-release.jks` أو أي keystore خاص بتوقيع APK بدلاً منه.

1. GitHub Actions يحتاج السر `BAKERY_LICENSE_PRIVATE_KEY_B64`.
2. يمكن أن يحتوي هذا السر على مفتاح الترخيص الخاص بصيغة PEM مباشرة، أو Base64 لمحتوى PEM، أو Base64 لمفتاح DER بصيغة PKCS#8 أو PKCS#1.
3. قبل النشر، يحول سير العمل المفتاح إلى PKCS#8 DER، ويختبر توقيعاً حقيقياً مقابل المفتاح العام المضمّن في التطبيق. إذا لم يتطابق الزوج يتوقف قبل نشر Worker.
4. بعد نجاح المطابقة، يزامن سير العمل المفتاحين إلى Cloudflare باسمَي `LICENSE_PRIVATE_KEY_PKCS8_B64` و`LICENSE_PUBLIC_KEY_DER_B64`.
5. يجب أن توجد كلمة مرور الإدارة في Cloudflare باسم `ADMIN_PASSWORD`، أو الاسم القديم `Admin_BassworD` مؤقتاً. يوصى بتوحيدها على `ADMIN_PASSWORD` وأن تكون 32 حرفاً عشوائياً على الأقل.
6. لا تحتاج إلى Termux في الإعداد أو التشغيل المعتمد. لا تستخدم إلا مفتاح الترخيص الخاص الأصلي المطابق للمفتاح العام داخل التطبيق. إذا لم يعد هذا المفتاح متاحاً، لا تستبدله بمفتاح APK ولا تنشئ مفتاحاً عشوائياً؛ يلزم إجراء تدوير مفاتيح مستقل وتحديث التطبيق.
7. احفظ المفتاح الخاص في GitHub Secret باسم `BAKERY_LICENSE_PRIVATE_KEY_B64` بصيغة PEM أو Base64 صحيحة. سير النشر يتحقق من صحة المفتاح ومطابقته للمفتاح العام قبل لمس قاعدة البيانات أو نشر Worker.
8. لا تضع المفتاح الخاص في المستودع أو التطبيق أو الموقع أو المحادثة أو واتساب. لا تستخدم مفتاح APK لتوقيع تراخيص العملاء.

## أسرع إعداد لمرة واحدة

1. في GitHub افتح Settings ثم Secrets and variables ثم Actions.
2. استبدل `CLOUDFLARE_API_TOKEN` برمز Cloudflare API Token جديد صالح. لا تستخدم Global API Key أو رابط لوحة Cloudflare أو نصاً يحتوي على `Bearer`.
3. يجب أن يملك الرمز صلاحيات الحساب المحدد: Workers Scripts Edit وD1 Edit. لا تمنحه صلاحيات أوسع من اللازم.
4. تحقق أن `BAKERY_LICENSE_PRIVATE_KEY_B64` يحتوي مفتاح الترخيص الخاص الصحيح المطابق للمفتاح العام الموجود في التطبيق. لا تنسخ مفتاح توقيع APK.
5. في Cloudflare Worker تأكد من وجود `ADMIN_PASSWORD` بطول 32 محرفاً على الأقل. الاسم القديم `Admin_BassworD` مدعوم مؤقتاً، لكن الأفضل توحيده على الاسم الجديد.
6. شغّل سير `Deploy bakery licensing Worker` يدوياً مرة واحدة. لا تعتبر النشر ناجحاً إلا إذا انتهى بالنجاح واجتازت فحوص health وadmin-config وsigning-pair.

إذا ظهر الخطأ `6003 Invalid request headers` فهذا يعني أن قيمة `CLOUDFLARE_API_TOKEN` ليست رمز API Token صالحاً بصيغة Bearer. أنشئ رمزاً جديداً والصقه كما هو دون بادئة أو اقتباس. لا ترسل الرمز إلى المحادثة.

إذا ظهر `LICENSE_PRIVATE_KEY_INVALID` أو `invalid-base64` فهذا يعني أن سر المفتاح الخاص غير صالح أو تالف. لا تحاول إصلاحه بإضافة نصوص أو مسافات. استبدله بالمفتاح الأصلي الصحيح بعد التحقق من مطابقته للمفتاح العام.

## التشغيل المعتمد دون Termux

لا يحتاج المالك أو العميل إلى Termux في دورة البيع اليومية. كل إصدار يتم من لوحة الإدارة عبر Worker.

1. يرسل العميل الطلب من صفحة الاشتراك. يجب أن يعيد Worker رقم طلب وحالة `pending` قبل اعتبار الطلب مسجلاً.
2. يرسل العميل صورة الإيصال عبر واتساب.
3. يتحقق المالك من وصول المبلغ فعلياً، ثم يسجل الدخول إلى لوحة الإدارة.
4. يفحص المالك جاهزية مفتاح التوقيع، ثم يعتمد الطلب أو يرفضه مع كتابة سبب الرفض.
5. يعرض النظام رمز التفعيل بعد الاعتماد فقط. ينسخه المالك ويرسله إلى رقم العميل الصحيح عبر واتساب.

### إعداد الخادم لمرة واحدة

من Cloudflare Dashboard افتح Worker باسم `al-mizan-bakery-licensing` ثم Settings ثم Variables and Secrets. اضبط الأسرار التالية:

- `LICENSE_PRIVATE_KEY_PKCS8_B64`: مفتاح ترخيص خاص صحيح بصيغة Base64 لمحتوى PKCS#8 DER، ويجب أن يطابق المفتاح العام المضمّن في التطبيق.
- `LICENSE_PUBLIC_KEY_DER_B64`: المفتاح العام بصيغة Base64 DER المطابق للمفتاح الموجود في التطبيق.
- `ADMIN_PASSWORD`: كلمة مرور إدارة قوية بطول 32 محرفاً على الأقل.

لا تضع المفتاح الخاص في صفحة المتجر أو لوحة الإدارة أو التطبيق أو المحادثات. لا تستخدم مفتاح توقيع APK.

### بوابة الجاهزية قبل البيع

- `/diagnostics/admin-config` يجب أن يعيد `adminPasswordConfigured: true`.
- `/diagnostics/signing-pair` يجب أن يعيد `signingReady: true` و`signingPairMatches: true`.
- جرّب طلباً وهمياً، ثم ارفضه بسبب واضح. تأكد من عدم إصدار رمز.
- جرّب طلباً وهمياً آخر واعتمده بعد التحقق من الإعداد. تأكد من ظهور الرمز للمدير فقط.
- تأكد أن الاستعلام العام عن الطلب لا يعرض رمز التفعيل أو بيانات العميل.
- اختبر إدخال الرمز في جهازه الصحيح ورفضه على جهاز آخر.

إذا فشل نشر Worker بسبب رمز Cloudflare API، لا تعتبر تغييرات GitHub منشورة على الخدمة الحية. أصلح صلاحية رمز النشر أو حدّث Worker من لوحة Cloudflare، ثم أعد اختبارات الجاهزية. لا تستخدم Termux كجزء من مسار العميل أو الإدارة.

## ضوابط إضافية

- يرفض Worker مرجع التحويل الذي سبق استخدامه في طلب معلق أو معتمد.
- يحد Worker من الطلبات العامة إلى 8 طلبات لكل عنوان IP خلال 15 دقيقة.
- طلب التفعيل يرسل إصدار التطبيق، ويرفض الخادم إصداراً لا يطابق الإصدار المنشور.
- لا يعرض الاستعلام العام بيانات العميل أو رمز التفعيل.
- استعادة رمز صادر سابقاً متاحة للمدير الموثق فقط، وتتطلب سبباً مسجلاً في سجل التدقيق. لا تنشئ الاستعادة ترخيصاً جديداً.

## قاعدة بيانات التراخيص

- قاعدة D1: `al-mizan-bakery-licenses`.
- مخطط الجداول: `licensing/schema.sql`.
- سير نشر Worker يطبق المخطط باستخدام `CREATE TABLE IF NOT EXISTS` قبل النشر.
- جداول الطلبات وسجل التدقيق يجب أن تكون موجودة في D1 الحية قبل تجربة دورة الطلب والاعتماد.

## اختبار الجاهزية

لا تعتمد البيع إلا بعد اجتياز جميع البنود:

- [ ] فحص `/diagnostics/admin-config` يعيد `adminPasswordConfigured: true`.
- [ ] فحص `/diagnostics/signing-pair` يعيد `signingReady: true` و`signingPairMatches: true`.
- [ ] إرسال طلب تجريبي يظهر بحالة `pending`.
- [ ] رفض طلب غير مدفوع لا يصدر رمزاً.
- [ ] اعتماد طلب تجريبي بعد التحقق من الدفع يصدر رمزاً واحداً فقط.
- [ ] الرمز يعمل على الجهاز المحدد ويرفض جهازاً آخر.
- [ ] الشهري والسنوي ينتهيان حسب المدة، والدائم الجديد يعمل بعد تحديث التطبيق.
- [ ] تحديث 2.6.17 فوق النسخة المثبتة يحافظ على البيانات والتوقيع والترخيص.
- [ ] النسخ الاحتياطي والاستعادة يحافظان على بيانات النشاط.
- [ ] الاختبار اليدوي يؤكد أن هامش الربح يساوي مجموع التحصيلات النقدية وبنكك والديون ناقص تكلفة التشغيل المستهلكة، بما فيها الجاز.
